## 4. HTTP security headers

### 4.1 Backend (Spring Security) — changed and tested

| Header | Before | After |
|---|---|---|
| `Content-Security-Policy: frame-ancestors 'none'` | present | present |
| `Referrer-Policy: no-referrer` | present | present |
| `X-Frame-Options: DENY` | Spring default | still present (default retained) |
| `X-Content-Type-Options: nosniff` | Spring default | now **explicit** so a framework default change cannot silently remove it |
| `Permissions-Policy` | absent | `camera=(), microphone=(), geolocation=()` |
| `Strict-Transport-Security` | **absent** | **config-gated**: emitted only when `HSTS_ENABLED=true` **and** the request is secure |

HSTS is deliberately opt-in (`app.security.hsts-enabled`, default `false`). Sending it from a host that
cannot consistently serve HTTPS locks users out for a year — the directive's warning is correct. Staging and
production set `HSTS_ENABLED=true` in `render.yaml`; `application-prod.yaml` also pins
`server.forward-headers-strategy: framework` so `request.isSecure()` reflects Render's
`X-Forwarded-Proto` instead of always being false behind the proxy.

`includeSubDomains` is explicitly **off** (the Spring default is *on*, which would bind every sibling
subdomain of the deployment domain) and `preload` is off (irreversible).

### 4.2 Frontend (Netlify) — corrected a false claim

`frontend/netlify.toml` previously stated *"HSTS is applied by Netlify's HTTPS layer"*. That is not true —
Netlify does not add HSTS by default. Now declared explicitly:

```toml
Strict-Transport-Security = "max-age=31536000"
X-Content-Type-Options    = "nosniff"
X-Frame-Options           = "DENY"
Referrer-Policy           = "strict-origin-when-cross-origin"
Permissions-Policy        = "camera=(), microphone=(), geolocation=()"
```

`includeSubDomains`/`preload` are omitted for the same reason as the backend.

### 4.3 Verified by test

`SecurityHeadersTest` (5 tests) and `HstsHeaderTest` (2 tests) boot the real filter chain:

| Assertion | Result |
|---|---|
| baseline headers present on a real response | PASS |
| HSTS **absent** when not enabled | PASS |
| HSTS **present** on a secure request when enabled | PASS |
| HSTS withheld on plain HTTP even when enabled | PASS |
| `includeSubDomains` / `preload` not emitted | PASS — *this test caught the Spring default; production code was corrected* |
| `X-Request-Id` generated when absent, echoed when safe, **replaced when unsafe** | PASS (3 tests) |

Full suite after the change: **417 tests / 64 suites / 0 failures**.

## 5. Rate limiting

**[O]** `LoginRateLimiter` is Bucket4j 8.0.1, in-process, keyed by `login:<email>:<remoteAddr>`, interval
refill 5 attempts / 60 s, max 10,000 buckets with a sweep. It returns **429** *before* any user lookup, so it
cannot be used for account enumeration. Login is the only throttled surface.

### Assessment

| Surface | Current | Adequacy for a single-instance pilot |
|---|---|---|
| Login (IP + account) | Bucket4j, in-process | **Adequate** — one instance; 429 verified |
| Account lockout | interval refill (no per-attempt leak) | Adequate |
| AI/tutor endpoints | **no server-side limit** | **Gap** — an authenticated user can drive unbounded provider spend |
| Generic API | none | Low risk; all authenticated |
| Multi-instance | limit resets per instance | **Gap for scale-out, not for staging** |

**[R] Before the pilot, add a per-user daily quota on the AI-cost endpoints** (`/api/tutor/*`,
`/api/quiz/{id}/answer` adaptive call, `/api/content/upload/*` generation). This is a product-cost control,
not just a security one: every uncapped call spends the owner's provider credits. It is not implemented here
because the quota values are a business decision (how many tutor turns per learner per day) and the
model/cost baseline must come from the AI service owner.

**[R]** For horizontal scaling, swap `LoginRateLimiter`'s `ConcurrentHashMap` for a Redis/Bucket4j-Redis
store. No Redis exists in the current architecture (`render.yaml` provisions none), so this is a
scale-out task, not a staging blocker. The class already isolates the decision behind `tryAcquire(key)`.

## 6. Monitoring

**[O]** There is **no Sentry (or equivalent) integration** anywhere: `git grep -il sentry` across
`backend`, `ai-elewa` and `frontend/src` returns only an unrelated test string.

### Implemented now (verifiable without a vendor account)

**Request correlation.** New `RequestCorrelationFilter`:

- accepts an inbound `X-Request-Id` only if it matches `^[A-Za-z0-9._-]{8,64}$`, otherwise generates a UUID
  (untrusted input can never be reflected or injected into logs);
- returns it as `X-Request-Id`;
- puts it in the SLF4J MDC, rendered by the new log pattern `%5p [%X{requestId:--}] %logger{36} - %msg%n`;
- clears the MDC in a `finally` block so pooled threads cannot mislabel the next request.

This makes a single client-visible failure traceable to one log line — the precondition for any error
aggregator to be useful.

### Not implemented, and why

| Requirement | Blocker |
|---|---|
| Error capture (Sentry backend/AI) | Needs a DSN and an account decision. Wiring an SDK with no DSN cannot be verified, and an unverified integration would be reported as "done" while capturing nothing. |
| AI provider failure/latency metrics | The AI service already classifies errors (`ERROR_TIMEOUT`, `ERROR_RATE_LIMIT`, `ERROR_SCHEMA_INVALID`, `retry_cause`) and logs them — **[O]** read from `ai_client.py`/`models/errors.py`. Shipping them to a dashboard requires the same vendor decision. |
| Uptime/health alerting | Render/Netlify provide health checks (`/actuator/health`, `/health`); alert routing needs the account. |

**[R]** Add Sentry with `sendDefaultPii=false` and a before-send scrubber that drops `learner*`, `prompt`,
`response` and any cookie/authorization header. Learner content must never leave the platform.
